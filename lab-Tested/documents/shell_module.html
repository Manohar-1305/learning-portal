Ansible Shell Module — Complete Guide

The ansible.builtin.shell module executes commands on managed hosts through a shell, usually /bin/sh. It supports shell features such as pipes, redirection, command chaining, and environment-variable expansion.

Lab environment: The Ansible controller runs Ansible commands. The managed host is ansible-client. Run the commands below from the controller terminal, unless otherwise specified.

1. Understand the module syntax

BASH — COMMAND
ansible ansible-client -m ansible.builtin.shell -a 'uptime'
  • ansible: starts the Ansible ad-hoc command-line tool.
  • ansible-client: identifies the managed host in the inventory.
  • -m: specifies which Ansible module to execute.
  • ansible.builtin.shell: selects the built-in shell module.
  • -a: supplies arguments to the selected module.
  • 'uptime': the shell command executed on the managed host.

Expected result

EXAMPLE OUTPUT
ansible-client | CHANGED | rc=0 >>
 20:10:15 up 2 days, 3:21, 1 user, load average: 0.02, 0.04, 0.01

The actual output depends on the managed host. The rc=0 value indicates that the command exited successfully. Ansible may report CHANGED for shell commands because it generally cannot determine whether an arbitrary command changed the system.

2. Execute multiple commands

BASH — COMMAND
ansible ansible-client -m ansible.builtin.shell -a 'whoami; hostname; date'

This runs three commands in sequence on ansible-client.

  • whoami: prints the effective username running the command.
  • ;: separates commands so the next command runs even if the previous one fails.
  • hostname: prints the managed host's hostname.
  • date: displays the managed host's current date and time.

3. Execute a command using a pipe

BASH — COMMAND
ansible ansible-client -m ansible.builtin.shell -a 'ps aux | grep sshd'
  • ps aux: lists running processes.
  • |: sends the output of the command on the left to the command on the right.
  • grep sshd: displays lines containing the text sshd.

The pipe is interpreted by the shell on the managed host. This is one reason to use the shell module rather than the command module. The output may include the grep process itself.

4. Redirect output to a file

BASH — COMMAND
ansible ansible-client -m ansible.builtin.shell -a 'echo "Ansible test" > /tmp/ansible-test.txt'
  • echo "Ansible test": produces the text to write.
  • >: redirects standard output into a file, replacing its previous contents if the file exists.
  • /tmp/ansible-test.txt: the destination file on the managed host.

Verify the file contents

BASH — COMMAND
ansible ansible-client -m ansible.builtin.command -a 'cat /tmp/ansible-test.txt'

Expected output:

OUTPUT
Ansible test

5. Create a playbook using vi

Ad-hoc commands are useful for individual tasks. Playbooks let you organize multiple tasks in a reusable YAML file.

Step 1: Open or create the playbook.
BASH — CONTROLLER TERMINAL
vi shell-playbook.yml

vi opens the editor. If the file does not exist, it creates the file when you save it.

Step 2: Enter insert mode.

Press the i key to start inserting text.

Step 3: Enter the following complete playbook.
YAML — shell-playbook.yml
---
- name: Shell module example
  hosts: ansible-client
  gather_facts: false

  tasks:
    - name: Get system uptime
      ansible.builtin.shell: uptime
      register: uptime_output
      changed_when: false

    - name: Display uptime
      ansible.builtin.debug:
        var: uptime_output.stdout

    - name: Check hostname
      ansible.builtin.shell: hostname
      register: hostname_output
      changed_when: false

    - name: Display hostname
      ansible.builtin.debug:
        var: hostname_output.stdout

Understand every playbook field

  • ---: marks the beginning of the YAML document.
  • - name: gives the play a readable description.
  • hosts: ansible-client: selects the managed host. This name must match an inventory host or group.
  • gather_facts: false: disables automatic fact gathering for this play.
  • tasks:: begins the list of tasks to execute.
  • - name: describes an individual task.
  • ansible.builtin.shell: uptime: executes the uptime command through a shell.
  • register: uptime_output: saves the result returned by the task in a variable.
  • changed_when: false: reports this task as unchanged, appropriate here because uptime only reads system information.
  • ansible.builtin.debug: displays information during playbook execution.
  • var: uptime_output.stdout: prints the standard output captured by the registered task.

The hostname tasks follow the same pattern. The first runs hostname and registers its result; the second displays hostname_output.stdout.

Step 4: Save and exit vi.
  1. Press Esc to leave insert mode.
  2. Type :wq.
  3. Press Enter.

:w saves the file; :q exits the editor.

6. Validate and execute the playbook

Step 1: Check the YAML and playbook syntax

BASH — COMMAND
ansible-playbook --syntax-check shell-playbook.yml

This checks whether Ansible can parse the playbook. It does not execute the tasks or guarantee that the remote commands will succeed.

Step 2: Execute the playbook

BASH — COMMAND
ansible-playbook shell-playbook.yml

Ansible connects to ansible-client, executes each task in order, registers the command results, and displays the captured output.

Expected result

EXAMPLE OUTPUT — VALUES WILL VARY
TASK [Get system uptime] ************************
ok: [ansible-client]

TASK [Display uptime] ***************************
ok: [ansible-client] => {
    "uptime_output.stdout": "20:10:15 up 2 days, 3:21, 1 user, load average: 0.02, 0.04, 0.01"
}

TASK [Check hostname] ***************************
ok: [ansible-client]

TASK [Display hostname] *************************
ok: [ansible-client] => {
    "hostname_output.stdout": "ansible-client"
}

PLAY RECAP ****************************************
ansible-client : ok=4 changed=0 unreachable=0 failed=0

7. Specify the working directory

YAML — TASK
- name: List files in /tmp
  ansible.builtin.shell: ls -la
  args:
    chdir: /tmp
  changed_when: false
  • args:: supplies additional arguments to the module.
  • chdir: /tmp: changes to /tmp on the managed host before executing the command.
  • ls -la: lists directory entries, including hidden entries, with detailed information.
  • changed_when: false: prevents this read-only listing task from being reported as changed.

8. Shell module versus command module

Shell module: invokes a shell, so pipes, redirection, and shell syntax work.

Command module: executes a command without shell interpretation. It is preferable for simple commands.

BASH — SHELL MODULE
ansible ansible-client -m ansible.builtin.shell -a 'hostname; uptime'
BASH — COMMAND MODULE
ansible ansible-client -m ansible.builtin.command -a 'hostname'
Important: Shell commands can have side effects. Use them only when needed, quote variables carefully, and avoid inserting untrusted input into shell commands. For file management, packages, and services, prefer dedicated Ansible modules.
